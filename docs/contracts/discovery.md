# Discovery

- **Decision:** D63. Supersedes D43 except that the signer only signs. Amends D62 (1).
- **Plan:** [discovery-service](../exec-plans/completed/discovery-service.md) (built 26 October to 5 November; removed here).
- **Code:** `adapters/sdk.py` (`HttpDiscoverySource`), `adapters/discovery_inventory.py`, `contracts/discovery.py`; `services/runner_list.py` for the list a clearinghouse serves.
- **Status:** the engine reads livepeer/node's `/discovery` contract through one HTTP source. It does not know which process serves that URL.

## What the engine reads

`LPB_DISCOVERY_URL` is required to start the engine, and the engine does not fall back to a built-in list. The address is checked when the engine starts, not when settings are read (#154): `EngineSettings` without it is valid, with `discovery_url` as `None`, and `start()` refuses before it polls or writes anything, with a `ValueError` that names the variable. A command that builds an engine and never starts it (`lpb purge`, `lpb bootstrap-admin`) needs no address. `BuilderEngine.create` opens the database, and migrates it when `LPB_AUTO_MIGRATE` is `true`, before `start()` can refuse: `serve` and `build_app` ask for the address before they build the engine, and an application that starts its own engine calls `settings.require_discovery_url()` before `create`. An engine whose `decorate` stage replaces the discovery source still needs `LPB_DISCOVERY_URL` to start, as it did before; whether such an engine should start without it is left open and is not changed here. `HttpDiscoverySource` sends `GET` to that URL with no credential and does not follow redirects. The URL may carry no userinfo, query or fragment, and the engine refuses one when settings are read: a failed refresh's error quotes the URL, and it goes to the log (`discovery.failed`). `/readyz` serves only a code as `discovery_error`, `unavailable` or `invalid_answer`, never the text (#113, C7; [RELIABILITY.md](../RELIABILITY.md#operations)). A 3xx is a failed refresh. Each poll has 5 seconds in all.

The body is a JSON array, the document livepeer/node's `livepeer-discovery` serves. `[]` is an empty inventory. A body that is not a JSON array fails the refresh, and the last good snapshot stays.

A document with records and no readable runner fails the refresh too (#114, C28). It is an answer the engine could not read, not an empty inventory: the reader skipped at least one entry or runner and read none. The last good snapshot stays and ages as after any failed refresh, `discovery_error` is `invalid_answer`, and the log carries the counts, in `discovery.inventory_skipped` and in the text of `discovery.failed`. Before, one bad publish emptied the catalog for every application. A truly empty answer still replaces the snapshot: `[]`, a document of metadata entries only, or orchestrator entries whose `runners` lists are empty. So does an answer with any readable runner, whatever share of its records was skipped; there is no threshold. A supplied `DiscoverySource` that returns no runners is an empty answer as before.

What a supplied `DiscoverySource` returns is checked before any of it is read (#158). A tuple or a list of `Runner` objects is an answer, and any other sized collection of them reads the same. Anything else fails the refresh as a source that raises does: `None`, a number, text, bytes, a mapping, a generator, one `Runner` in no list, or a collection in which any item is not a `Runner`, whatever the other items are. The last good snapshot stays and ages, `discovery_error` is `invalid_answer`, and the text of `discovery.failed` names the type that came and quotes nothing of it. An engine whose source answers so the first time starts, with no snapshot, as it does when its source raises. Empty text, empty bytes and an empty mapping are not an empty inventory: only a collection with no runner in it is. `NotRunners` in `services/discovery.py` is the error, and `tests/unit/test_supplied_discovery_source.py` has the cases.

The dev stack points the URL at livepeer/node's `livepeer-discovery`, run in static mode (`deploy/dev-stack/config/discovery.toml`). The node commit that stack builds is recorded in [upstream-baseline.md](../references/upstream-baseline.md).

## How a document is read

The reader takes the fields it stores. An entry is read when `address` is a URL the engine can call and `runners` is a list. A metadata entry (`nodes`, no `address`, and no `runners` or an empty list) yields no runners. An entry with `nodes`, no `address` and anything else under `runners` is not metadata, so it is a skipped entry (#114, C28): no address can read records there, and a value that is no list (`null`, `{}`, `""`, `false`) is not an empty one. A runner is kept when `url` is a URL the engine can call, `app` is valid text of 1 to 200 characters, and `observed_at` is an RFC 3339 timestamp that converts to UTC.

Valid text is a JSON string of valid Unicode with no control character (#114, C12). In an optional field (`mode`, `version`, `metadata`, a price's `currency` and `unit`, a GPU's `id` and `name`) a tab, a newline and a carriage return are allowed: they can be stored and served, and metadata is often JSON written over several lines. `app` and `url` allow none. A lone surrogate is not valid Unicode: JSON can carry one as `\ud800`, and the catalog could then not be written as JSON, so `GET /v1/offerings` answered 500 for every application. A control character is U+0000 to U+001F or U+007F to U+009F; PostgreSQL refuses the first of them, NUL, in text. A runner whose `app` or `url` is not valid text, or whose `app` is longer than 200 characters (the longest app a job can name and the store can keep), is skipped and counted like any other bad record. Any other text field that is not valid text reads as absent, and the runner stays: `mode`, `version`, `metadata`, the `currency` and `unit` of `price_info`, and the `id` and `name` of `gpu`. A price whose currency or unit is absent cannot be paid. Nothing is rewritten: text is kept exactly as advertised or not read.

A URL the engine can call is `http` or `https`, has an ASCII host the engine's HTTP client connects to as written and, if any, a port from 1 to 65535, and holds no ASCII space (U+0020), control character (U+0000 to U+001F and U+007F to U+009F, so no tab or line break) or lone surrogate: it is valid text as above, and a space would split the request line. No other space character is refused: a no-break space (U+00A0), a line separator (U+2028) or an ideographic space (U+3000) in a URL's path is kept. The engine percent-encodes such a character in the runner URL's path when it calls the runner (`%C2%A0`), by the rule it applies to a job's path ([engine.md](engine.md#jobs-and-attempts); #113, C3). aiohttp folds a non-ASCII host, so `https://①27.0.0.1` would reach `127.0.0.1` under a name the payment-origin check never sees; a host written in punycode (`xn--`) is read. It has no userinfo, query or fragment: the engine appends each request's path to a runner URL, an `address` whose origin matches that URL becomes `orchestrator_url` for the payment-origin check, and error text quotes both. Node's schema allows those three on a runner URL; the engine does not. One bad record is skipped on its own. The skip is logged as `discovery.inventory_skipped` with a count of skipped entries and a count of skipped runners. The rest of the document is kept. When nothing is left to keep, the refresh fails ([above](#what-the-engine-reads)).

The text rule holds for any `DiscoverySource`, not only the reader (#114, C12). A source supplied through `decorate` builds its `Runner`s itself, and `Runner` does not check its text. So `DiscoveryService.refresh` checks every runner a source returns with `has_storable_text` (`contracts/discovery.py`), the rule the reader uses: `url`, `app` and `orchestrator_url` are valid text with no control character, and each optional text field is absent or valid text that may hold a tab or a line break. A runner that fails it is skipped whole and counted in `discovery.inventory_skipped` (`entries` is 0); the other runners are kept and the refresh succeeds. Only the reader reads a bad optional field as absent. The rest of this section (a URL the engine can call, an `app` of at most 200 characters, a readable `observed_at`) is the reader's and is not checked on a supplied source's runners.

There is no size limit, no stamp-age filter, and no de-duplication. An integer field reads any whole JSON number node accepts (`3`, `3.0`, `3e0`) that fits 64 bits. A price string, a fractional capacity, or any other optional field of the wrong type is absent, and the runner stays. `capacity_available` is the exception: a missing one is unknown, which selection treats as one free slot, but a value that is present and not an integer reads as 0, so that runner is tried last. livepeer/node is stricter from v1.0.7 (node #82): its decoder skips a runner whose optional field has the wrong type, that repeats a key, or that writes a key in another letter case, so behind `livepeer-discovery` at that version such a record does not reach the engine. The reader keeps its own rule for every source; `tests/unit/test_discovery_reader.py` lists node's v1.0.7 cases by name, with the ones the reader keeps and node drops.

Numbers are read as exact decimal tokens ([RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)), never as binary floats. A token `Decimal` cannot hold still counts as a number: the runner is kept, that field is absent, and the payment layer reports that the price cannot be paid.

## Schema fields and `Runner`

`address` on an orchestrator entry becomes `orchestrator_url` only when its origin equals the runner URL's origin. A claimed address on another host is dropped, so `PaidRequest` will not sign a challenge whose `payment_url` is that host and `orchestrator_of` will not exclude it as a failover group. The pinned dump uses the same host for `address` and every runner URL, so those runners keep their address. `price_info` is kept as advertised: `price`, `price_usd`, `currency` and `unit`, all optional. `price` and `price_usd` are exact decimals when the token fits.

| Schema | `Runner` |
| --- | --- |
| entry `address` | `orchestrator_url` when its origin matches `url`; otherwise absent |
| `url`, `app`, `mode` | the same names. `app` is at most 200 characters |
| `observed_at` | `observed_at`, as UTC. A missing stamp, or one the clock cannot convert, skips the runner |
| `capacity`, `capacity_used`, `capacity_available` | the same names. There is no `session_ids` fallback |
| `price_info` | `price_info`, as advertised |
| `version`, `metadata`, `gpu` | the same names. The engine never interprets `metadata` |

`runner_id` is not in the schema and is not on `Runner`.

## Rules that apply after discovery

| Rule | Where |
| --- | --- |

| Rate age and `stale` | the catalog (D62 (3), `LPB_RATE_MAX_AGE_S`) |
| What advertised capacity means for a job | selection ([below](#advertised-capacity)) |

## Advertised capacity

`capacity_available` is a hint, never a gate (#114, C17). It is as old as the discovery snapshot, and a runner that was full then may have room now. A runner that advertises `0` stays in selection: the default policy (`MostCapacityFirst`) orders runners by free capacity, most first, with unknown capacity as one free slot, so a zero-capacity runner is tried after every runner with room. On a job that pays, that order holds within two parts, not across them: the engine first moves the free runners and those whose price the signer takes a ceiling for ahead of the rest (`capped_first`), so a priced zero-capacity runner is tried before a runner with room and no price the signer pays.

When every runner for an app advertises `0`, what the engine does depends on whether an attempt would sign a payment. A full runner's 503 can come on the paid request, after the signer signed, and a ticket an orchestrator rejects after signing is still charged ([payments.md](payments.md#cost-classification)). livepeer/node before v1.0.7 asks a priced single-shot request for payment before it looks at capacity, so there a full runner always refuses after signing. Since v1.0.7 the node looks first (`challenge` in `orchestrator/payment.go` calls `checkCapacity`, node #67): a full runner answers the unsigned request with 503 and nothing is signed. That check reserves no slot, so a slot taken between the challenge and the paid request is still refused after signing. The engine does not know which node version an orchestrator runs, so the rule is the same for all of them. The engine then tries only the runners an attempt signs nothing for. On an unpaid job (a transport with no signer) that is every runner. On a job that pays it is the free runners and those with no price the signer takes a ceiling for, which are refused at their 402 unsigned. They are tried anyway, up to the job's `max_attempts`: the hint can lag, and asking costs nothing. If no such runner is left, the job fails `no_capacity` before any attempt: no runner is asked, nothing is signed, REST answers 503 with `Retry-After: 5`, and the same `operation_ref` runs again ([engine.md](engine.md#failures)). When at least one runner advertises room or an unknown capacity, every runner stays a candidate on a paying job too, and an attempt on a priced zero-capacity runner, tried last, is a paid one.

That last rule is a decision, not an oversight (#158; Mike, 26 November 2026): the rule for an app whose every runner advertises `0`, no paid attempt on such a runner, is not extended to an app where a runner has room. A capacity figure is a hint that can lag behind the runner, so a runner that advertises zero is tried last and is not ruled out while others have room. What it costs is one signed payment for a refusal, when the runners with room have failed and the hint was right. "Tried last" is last of the runners the job pays, by the order of the first paragraph: if the only runners with room are ones the job signs nothing for (no price, or a price the signer takes no ceiling for), the priced zero-capacity runner is the first runner tried, and the attempt is paid. A queued job follows the same rule as an immediate job and a stream, since one function chooses the runners for all three (`JobRunners.choose`, `services/job_runners.py`): with any runner that has room it does not wait ([engine.md](engine.md#running)).

If every runner tried refuses, the job fails `refused` through the normal failover path: 503 with `Retry-After: 5`. The engine's own admission limits are not a job failure: a full engine or app raises `NoCapacity` (REST 503 with `Retry-After`) before any job is written. The catalog is unchanged: `ready_count` still counts the runners with unknown or positive capacity, so an app whose every runner advertises `0` shows `ready_count` 0 and can still run a job.

There is no setting for this. An operator who wants zero-capacity runners dropped supplies a `SelectionPolicy` that leaves them out; a job whose policy returns no runner fails `no_offering` ([extending-the-engine.md](../design-docs/extending-the-engine.md#rules-every-implementation-must-keep)).

## Sources

Any process that serves this contract can sit behind `LPB_DISCOVERY_URL`. One orchestrator's own `/discovery` is such a process, and so is a payment clearinghouse's runner list ([above](#the-clearinghouses-runner-list)), for a reader that sends a credential. The reference implementation these docs name is livepeer/node's `livepeer-discovery`. The dev stack runs it in static mode (`deploy/dev-stack/config/discovery.toml`).

That process GETs each listed orchestrator at startup and every `RefreshInterval` (30s in the dev stack; the process default is 5 minutes) and verifies TLS with the system trust store. A failed refresh keeps the last successful snapshot until `MaxFailedRefreshes` consecutive failures. The default is 6, and the dev stack does not override it. A TLS failure, a non-200, or a document `Decode` rejects counts as one failure. A source that has never succeeded stays out of the inventory. A runner with no `observed_at`, or one more than 30 seconds ahead, is skipped inside `Decode`. That skip does not drop the source when another runner in the same document is valid.

## The clearinghouse's runner list

A payment clearinghouse publishes its runner list, and an enterprise's engine reads that list by default (D87, #166): its `LPB_DISCOVERY_URL` is `https://<clearinghouse>/v1/clearinghouse/discovery`. Nothing is enforced at signing in this version, so an enterprise may point at a source of its own.

- **What is served.** The document the clearinghouse's own `HttpDiscoverySource` last read from its `LPB_DISCOVERY_URL`, byte for byte, as `application/json`. It is livepeer/node's document, not a copy in another shape: nothing is parsed and written again, no schema is vendored, every number keeps its digits, and a field or a record the reader skips is still there. An engine reading the route therefore reads what the clearinghouse read, by the same rules, and holds the same runners (`tests/unit/test_clearinghouse_discovery.py` reads the pinned node dump through the route with today's reader).
- **Who may read it.** Any credential of a tenant, which at a clearinghouse is its admin's or its auditor's key, and a clearinghouse admin. An actor key is 403, a payment key 401, and no credential 401.
- **The reader carries the tenant admin key there, and nowhere else** (#168). `HttpDiscoverySource` sends no credential to livepeer/node's open `/discovery`. An engine that uses a clearinghouse (`LPB_CLEARINGHOUSE_URL`) has the clearinghouse's runner list as its default `LPB_DISCOVERY_URL`, and its reader then sends `Authorization: Bearer <the tenant admin key>` (`LPB_CLEARINGHOUSE_TOKEN`). The key is sent only when the discovery address is that route exactly: the same scheme, host, port and path as `LPB_CLEARINGHOUSE_URL` followed by `/v1/clearinghouse/discovery`. An enterprise that points `LPB_DISCOVERY_URL` at a source of its own sends it no key, and no redirect is followed. The list is the same for every tenant, so the reader does not ask whose key it carries (#165): a refresh reads no grant, and a key that belongs to another tenant than `LPB_CLEARINGHOUSE_TENANT_ID` still reads the list. That key is refused everything else it is sent with, and a job sends it nowhere ([payments.md](payments.md#who-the-engine-is-at-the-clearinghouse)). Without the key the refresh fails with the route's 401, and the engine keeps its last good snapshot. A read that carried the key and failed (an error status, a redirect, a timeout, no connection, an answer it cannot read) raises an error of the kind the reader always raised, with the same words, that leads to no key: it holds no request, chains none that does, and was never in a frame that held one. A reader with no credential raises the HTTP client's own error, as before.
- **When the clearinghouse's source is down.** The route serves the last document that read, however old: it is what the clearinghouse's engine itself would run a job on, since a failed refresh keeps the last good snapshot ([above](#what-the-engine-reads)). `observed_at` on each runner still says how old the record is, so the reading engine's catalog marks its rates `stale` by `LPB_RATE_MAX_AGE_S`, as the clearinghouse's does. The clearinghouse's own `GET /readyz` shows the failure (`discovery_error`).
- **Before any document was read** the route is 503 with `Retry-After: 5`. It is never an empty list in place of an unknown one: a reader would replace its snapshot with it. A 503 is a failed refresh there, which keeps what the reader had.
- **Optional.** The route is present when the discovery source holds the document it read (`DiscoveryDocumentSource` in `protocols`, which `HttpDiscoverySource` has). A source supplied through `decorate` that holds none, such as a wrapper that filters runners, serves no route: `engine.runner_list` is `None`. The engine does not write a node document from its `Runner`s.
- **The halves stay apart.** The route is the clearinghouse half's and the discovery service the work half's. The route reaches the document through that port on the discovery source, and `services/runner_list.py` imports nothing of `services/discovery.py` (`tests/structure/test_two_halves.py`). The engine's refresh loop is what reads the source, so a deployment that serves the route keeps that loop running.

## Testing

The reader is tested against the node commit [upstream-baseline.md](../references/upstream-baseline.md) pins, without a copy of node's schema. `tests/unit/node_discovery_eee09c4.json` is what that commit's `livepeer-discovery` served at `/discovery` for ai1 and xodeapp, and every runner in it must read with its exact price. Node's own `discovery/schema_test.go` cases for the fields the engine needs are kept by name in `tests/unit/test_discovery_reader.py`. What the engine does with text it cannot keep, with an answer it cannot read and with zero advertised capacity is in `tests/unit/test_runner_text.py`, `test_unreadable_discovery_answer.py` and `test_zero_capacity.py`, written against the catalog, the jobs, health and the log, not the reader (#114): they carry into ISS-48. When the pin moves, capture the document again from that commit's `livepeer-discovery` (`GET /discovery`, or `--dump`).

`FakeDiscoveryService` (`livepeer_builder.testing`, test-only) serves a node-format document, including `observed_at` by default, through an in-memory HTTP client into the real `HttpDiscoverySource`. `make_engine(runners=…)` keeps that signature and is built on it, so a test runs the same reader as production.

## `observed_at`

The reader keeps a runner when `observed_at` is an [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) timestamp, `T` and `Z` in either case, that it can convert to UTC. Nanoseconds truncate to microseconds. A runner that omits the stamp, uses another date format, or has a stamp the clock cannot hold (a leap second) does not appear. That includes orchestrators on livepeer/node `v1.0.2`. The catalog still treats a stamp it cannot use, from a source other than this reader, as the poll time (D62 (3)).

# M4 decisions

Accepted decisions for M4, reuse and reliability ([m3-decisions](m3-decisions.md) holds D29–D63). Each
row was locked by Mike in the question-by-question review of 12 and 13 November 2026. A row names the
earlier decision it amends. The detail of each answer is in the linked guide's "Questions locked" section,
or in the linked ticket.

| # | Decision | Where |
| --- | --- | --- |
| D64 | **M4 order of work: hardening first, the runner standard last** (Mike, 12 and 13 November 2026). (1) Every fix in the hardening tickets (#112 to #115) merges into `releases/m4` before any feature pull request, one small pull request per finding, test first. (2) The consumer apps pin `v0.2.0` now and that hardened commit next (#116); there is no patch release. (3) Runner contract v1 (ISS-47) is not vetted. ISS-48, its adoption, is the last feature of M4 and may move to M5; ISS-26 to ISS-30 no longer depend on it, route by app ID, and the criteria added to them on 5 November moved to ISS-48. (4) The parts of #73 and #86 outside the ISS-27 and ISS-46 guides are stretch tickets (#118 to #124) that do not gate M4. (5) The router split of #25 lands as a tidy-only pull request before ISS-26 | [index](m4-guides/index.md) |
| D65 | **Paid-path safety** (#112) (Mike, 12 and 13 November). (1) One attempt signs one payment plus `LPB_MAX_PAYMENT_CHALLENGE_RETRIES` retries, counted as signatures; unsigned refresh passes have their own limit of the same size. (2) Provisioning that cannot store the key is refused at startup and per request, before any provider call. (3) With auto-migrate off, a database revision that differs from the package's stops the engine at startup. (4) Amounts are validated at the contract, in the provider's format (unsigned decimal, at most 18 fractional digits), with a fixed upper bound and no operator ceiling. (5) `lpb smoke` always uses a temporary database, and no command that never asks discovery requires `LPB_DISCOVERY_URL` | #112 |
| D66 | **Request-boundary hardening** (#113) (Mike, 12 November). (1) A job path must already be normal: no `.` or `..` segment, empty segment, backslash, control character or fragment; the adapter also confirms the address still begins with the runner's. (2) `/readyz` reports errors as fixed categories, never exception text. (3) Every id that enters a provider URL is percent-encoded, and `grant_id` is a checked id type. (4) An empty job `operation_ref` is a 422. (5) A bearer longer than 16 KiB, or one that cannot be read, is a 401. (6) Every path and query id is stored text, with a structure test. (7) A second `start()` is refused; a runner's content type passes through unchanged; a streamed answer's header send is inside the guarded block | #113 |
| D67 | **Untrusted upstream data** (#114) (Mike, 12 November). (1) A runner whose `app` or `url` is not valid, storable text is skipped alone. (2) A discovery answer with records but none readable is a failed refresh, and the last good snapshot stays. (3) Cost sync sets aside a usage row it cannot read or store, records it, and continues; a payment challenge with an unstorable manifest id is refused before signing. (4) One strict reader for every provider answer; a malformed page is a provider error, never an empty page. (5) Zero-capacity runners stay in selection, tried last, also when every runner says zero; a job refused by all of them fails `refused`, and `no_capacity` means only the engine's own admission limits | #114 |
| D68 | **Store concurrency and accounting integrity** (#115) (Mike, 12 and 13 November). (1) Each admin command writes only its own columns, with a condition in the SQL; nothing leaves `revoked`. (2) Reconciliation is per allocation, the current one by default, with an optional `allocation_id`. (3) Usage is written once in one guarded statement; an identical repeat answers 200 with the stored usage, and different quantities are refused. (4) `secret_ref` is unbounded text, as are the secret-reference columns planned for sessions and event subscriptions | #115 |
| D69 | **Async jobs** (ISS-26; Q1 to Q8 locked) (Mike, 13 November). (1) A repeated async submit returns the existing job. (2) After a restart only a `running` job with no attempt row is requeued, at most three times. (3) `POST /v1/jobs/{id}/cancel`, for queued jobs only. (4) A paid reply that could not be stored costs `failed_after_payment`. (5) Stored inputs and results are not encrypted by the engine in M4. (6) Defaults: 4 workers, 1000 queued, 1 hour in the queue, 16 MiB per result, results kept 7 days. (7) Polling only. (8) A job whose access key is revoked while it waits still runs | [guide](m4-guides/iss-26-async-jobs.md#questions-locked) |
| D70 | **Persistent sessions** (ISS-27; Q1 to Q8 locked). Amends D9's wording (Mike, 12 and 13 November). (1) ISS-27 is the session core, the HTTP, SSE and WebSocket proxy, `realtime-transcription` and the embedded `SessionManager`. (2) The engine sends a first `start` frame and a last `end` frame on a relayed socket, as #73 proposes. (3) `jobs.run` opens a session. (4) John arranges the GPU runner; a CPU-only WebSocket runner is the agreed fallback for the live evidence. (5) The job has mode `session`, and a repeated open returns the existing session. (6) Non-admin reads of a session job show a keyed hash in place of `manifest_id`. (7) Several Batteries sessions for one key match when the engine has one entry, built only if a live run shows the split. (8) Funding failures are what the SDK loop reports: `released` on a renewal 404, `funding_stopped` on any other 4xx except 408 and 429 | [guide](m4-guides/iss-27-persistent-endpoints.md#questions-locked) |
| D71 | **Failure classification and recovery** (ISS-28; Q1 to Q4 locked). Amends D57's list of jobs that never reached a runner (Mike, 13 November). (1) The cost class follows the job: a `succeeded` attempt is `delivered` only when its job succeeded. (2) A failure in the connect phase with nothing paid is `retry`, on a closed list of positively identified connect errors. (3) A runner's own 4xx is `validation` / `fix_request`, to be revisited when the runner standard is complete. (4) Health and reconciliation report costs that stay `pending` past a threshold | [guide](m4-guides/iss-28-failure-recovery.md#questions-locked) |
| D72 | **The REST contract** (ISS-29; Q1 to Q5 locked). Breaking for REST clients; amends D59's paging (Mike, 13 November). (1) ISS-29 does not wait for the events feed. (2) Errors are RFC 9457 problems with a stable `code` as an extension field. (3) Lists page with an opaque cursor and a `Link` header; `before` stays a date filter. (4) `whoami` is a facade member behind `GET /v1/me`. (5) Grant funding moves to `POST /v1/admin/grants/{id}/fund`, with no alias | [guide](m4-guides/iss-29-rest-coverage.md#questions-locked) |
| D73 | **MCP** (ISS-30; Q1 to Q7 locked) (Mike, 13 November). (1) The guide's tools plus `whoami` and `cancel_job`; `list_offerings` is compact and filterable. (2) `LPB_JWT_AUDIENCE` is a list. (3) A result over the cap carries no bytes and points to `mode="async"`. (4) HTTP only, no stdio. (5) `GET /mcp` answers 405. (6) Immediate `run_job` keeps the 300 second default and sends liveness progress. (7) The SDK's client in CI, and Claude Code as the pinned host for the evidence | [guide](m4-guides/iss-30-mcp.md#questions-locked) |
| D74 | **The second payment configuration** (ISS-31; Q1 to Q4 locked). Replaces the Mode B gap of D23 (Mike, 13 November). (1) Separately operated means `per_application` only in M4. (2) It is shown with two Compose projects on one host. (3) `LPB_SHARED_ALLOCATION_ID` stays a setting, and the read token keeps two permissions (T5 accepted). (4) The setting is `LPB_PAYMENT_OPERATION`, `self_operated` or `separately_operated` | [guide](m4-guides/iss-31-payment-configurations.md#questions-locked) |
| D75 | **The events feed** (ISS-46; Q1 to Q9 locked). Amends D10's scope rule (Mike, 12 and 13 November). (1) ISS-46 is the pull feed; push is stretch (#124). (2) An actor reads its own events; an auditor or admin reads its own application's. (3) Sequence numbers come from a counter row. (4) Any event retention is allowed, with one global floor. (5) A correction carries the new `JobCost` only. (6) No `job.started`. (7) No backfill. (8) Any change in a cost's content is a correction. (9) A restore changes the feed's `epoch` | [guide](m4-guides/iss-46-events-feed.md#questions-locked) |
| D76 | **Embedding and extensions** (ISS-32; Q1 to Q6 locked) (Mike, 13 November). (1) The examples move to `examples/` and run against the installed wheel. (2) The trusted-backend authenticator is not built in M4 (T7 moves to M5). (3) The candidate is a `v0.3.0rcN` tag on `releases/m4`. (4) The commerce fixture consumes the events feed from the start. (5) The router factories of #25 land first (D64). (6) `DefaultPolicy` is exported from the package root | [guide](m4-guides/iss-32-embedding-and-extensions.md#questions-locked) |
| D77 | **Replacing the reference app's access flow** (ISS-33; Q1 to Q4 locked). Amends D47 and D49 (Mike, 13 November). (1) ISS-33 does not wait for ISS-32. (2) The Keycloak realm gains a second application. (3) The access probe runs by hand once per release, with its evidence committed. (4) Admin and read-only admin come from a dedicated token claim; the admin scope settings and the denylist go (closes T19). Operators scoped to one application are a separate design ticket, #126 | [guide](m4-guides/iss-33-access-flow-replacement.md#questions-locked) |
| D78 | **The builder console's coverage of the job modes** (ISS-34; Q1 to Q4 locked) (Mike, 13 November). (1) The console reads the engine's `category` and `recovery` and holds no table of failure kinds. (2) It runs a session from an audio file, with the socket on its server side. (3) The async job is FLUX schnell. (4) The scripted engine for its browser test is a fixture script in the console's repository | [guide](m4-guides/iss-34-reference-app-coverage.md#questions-locked) |
| D79 | **Isolation, recovery and accounting replay** (ISS-35; Q1 to Q3 locked) (Mike, 13 November). (1) The rebuild check ships as `lpb costs verify`. (2) The `corrected` label depends on history and is left out of the rebuild comparison. (3) Retention and the cost data: the wrong match after a purge (R1) is fixed, and the engine keeps a running total of fees removed by retention so that reconciliation balances after a purge. The condition for that total, that reconciliation otherwise stops balancing (R3), was shown by test on 13 November, on SQLite. (4) The usage purge skips rows that a kept job still uses, so a kept job's cost is never recomputed from fewer rows (R4, found by the same tests) | [guide](m4-guides/iss-35-isolation-recovery-replay.md#questions-locked) |
| D80 | **The funded matrix** (ISS-36; Q1 to Q4 locked) (Mike, 13 November). (1) Seven rows. (2) A $3 cap across dry and final runs. (3) The evidence lives in builder-core. (4) M3 decision 8 carries over: the agent runs each step and Mike watches | [guide](m4-guides/iss-36-funded-matrix.md#questions-locked) |
| D81 | **Pins in M4** (#117) (Mike, 12 November). (1) The three upstream pins move early, one pull request each, each with a funded check on the dev stack: livepeer/node to a commit at or after `2364436`, Batteries to `v0.0.3`, the SDK to `7dc2a07`. (2) The SDK stays a git reference in M4 (T1 open; PyPI is decided in ISS-38). (3) #89 closes after one measurement taken after the node pin moves | #117 |

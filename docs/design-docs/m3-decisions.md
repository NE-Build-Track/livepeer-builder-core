# M3 decisions

Accepted decisions after the M2 close-out ([m2-decisions](m2-decisions.md) holds D1–D28).

| # | Decision | Where |
| --- | --- | --- |
| D29 | **Streaming is generic and per job** (Mike, 19 October, from the first enterprise reference app's requirement). `jobs.stream` delivers one runner response as bytes plus a content type; the engine never interprets the stream. `mode` stays `immediate`; async (M4) is untouched | [engine.md#streaming](../contracts/engine.md#streaming), [plan](../exec-plans/active/streaming-jobs.md) |
| D30 | **A stream the caller stops reading is `abandoned`, and the job `uncertain`** when payment went out (Mike, 19 October). The work was paid for and probably ran; the engine never pretends otherwise. `abandoned` is both an attempt outcome and a failure kind | [engine.md#streaming](../contracts/engine.md#streaming) |
| D31 | **Payment evidence is written before the first byte** of a stream, on the `in_flight` attempt, so a restart mid-stream resolves the job as `uncertain` (Mike, 19 October) | `services/jobs.py` |
| D32 | **`Runner` carries `version`, `metadata` and `gpu` as the node echoes them** (Mike, 19 October). The engine never interprets `metadata`; the chat runner publishes `{"model_id": …, "max_context": 131072}` there and ChatLPT reads it instead of paying for a models call | [engine.md#discovery](../contracts/engine.md#discovery) |
| D33 | **Streaming is optional for transports**: `StreamingRunnerTransport` adds `open`; a transport without it makes `jobs.stream` answer 400 rather than changing the `RunnerTransport` protocol every integrator implemented (Mike, 19 October) | `protocols/__init__.py` |
| D34 | **A stream's end is recorded by a task the caller cannot cancel** (Mike, 20 October). A client disconnect under Starlette/anyio cancels every await in the request task, so the job, attempt and slot are finished in their own task. The admission slot is always released; the writes are bounded by `LPB_STREAM_FINALIZE_TIMEOUT_S` (default 10 s), and a store failure leaves the job `running` for `recover_interrupted` | `services/streams.py`, `utils.run_shielded` |
| D35 | **Stream deadlines** (Mike, 20 October): `timeout_s` counts from the job's start and covers opening, and stops applying once the runner has ended the stream; `first_byte_timeout_s` (default 60 s, capped at `timeout_s`) bounds each runner request to its first chunk; `idle_timeout_s` now defaults to 60 s. First-byte and idle count only while the caller waits. A timeout never fails over. The transport enforces the first-byte limit and keeps the signed sessions; the engine stops a transport 5 s past it and treats the payment as sent | [engine.md#deadlines-d35](../contracts/engine.md#deadlines-d35) |
| D36 | **The engine owns open streams** (Mike, 20 October): `JobStream` is an async context manager; `engine.stop()` waits `LPB_STREAM_DRAIN_TIMEOUT_S` (default 30 s) for open streams, then abandons the rest and waits for any end still being written, so the store never closes under it; `timeout_s` ends a stream nobody reads; a failed write right after `open` closes the stream and keeps its manifests | [engine.md#how-a-stream-ends](../contracts/engine.md#how-a-stream-ends) |
| D37 | **REST streams fail visibly** (Mike, 20 October): the response headers wait for the runner's first chunk, so earlier failures use the ordinary mapping (504, 502); a failure after it aborts the connection instead of ending the body cleanly. The engine never writes into the stream (D29) | [engine.md#rest-d37](../contracts/engine.md#rest-d37), `http/streaming.py` |
| D38 | **"Done" comes from the caller or the runner, never from parsing** (Mike, 20 October): `JobStream.complete()` records `succeeded` with the bytes the caller read (never the engine's one-chunk read-ahead); a cancelled reader or disconnected client (D40) gives the runner `LPB_STREAM_SETTLE_S` (default 1 s) to end the stream, else `abandoned`; `aclose()` stops at once | [engine.md#how-a-stream-ends](../contracts/engine.md#how-a-stream-ends) |
| D39 | **Signed-session rows are append-only** (Mike, 20 October): `finish_attempt` adds manifests not stored yet and never rewrites a row, because cost sync owns the match columns. A stream writes its sessions twice (D31 and at the end) and must not reset a match made in between | `store/sql.py`, `protocols.JobRepo.finish_attempt` |
| D40 | **Closing the iterator is the caller stopping; a disconnect is said explicitly** (Mike, 21 October, from the PR #28 review): a `break`, `return` or error that closes or drops the stream's iterator records `abandoned` at once, like `aclose()`, even without `async with`. The settle window is only for cancellation and for `JobStream.disconnected()`, which an HTTP layer calls when its client goes away; the REST layer calls it on a failed or cancelled send, whichever way the server reports the disconnect. An iterator closing is not evidence the runner finished, and settling it kept funding and could count the read-ahead | [engine.md#how-a-stream-ends](../contracts/engine.md#how-a-stream-ends) |
| D41 | **Adapter contract for the SDK pin** (21 October, [PR #31](https://github.com/NE-Build-Track/livepeer-builder-core/pull/31); the pin is now upstream `76a1a1c`). (1) `on_payment_session` ([livepeer-python-gateway#81](https://github.com/livepeer/livepeer-python-gateway/pull/81)) is the sole source of `payment_sent`: signing runs ahead of the paid runner request, and if signing fails or times out before `on_payment_session` runs, no callback fires, `payment_sent` is `False`, and the job ends `failed` (or fails over on `payment_refused`). Once `on_payment_session` fires, `payment_sent` is `True` and a subsequent timeout or uncertain failure marks the job `uncertain`. (2) A missing `payload` (`None`) is sent as `{}` on buffered and streamed calls, as earlier pins did; the SDK alone would send an empty body | `adapters/sdk.py`; T14, T15 |
| D42 | **Payment evidence is stored when the signer signs, before the paid request** (Mike, 23 October, ISS-16, [PR #44](https://github.com/NE-Build-Track/livepeer-builder-core/pull/44)). The transport awaits `on_signed(manifest_id)` for each signed session, passed explicitly to `call` and `open`, and the engine writes `payment_sent` and the session on the `in_flight` attempt there, in a task the caller cannot cancel (D34). `record_payment_evidence` only appends (D39) and never touches outcome or timing, so a late report cannot reopen an attempt; on an ended job it increments the evidence version, so the stored cost projection is out of date. A failed write is logged and the call goes on; the write after the call, or the close after an error or cancel, stores the same sessions. A session reported through `on_signed` keeps the attempt paid even if the transport later says otherwise: no failover after payment | `services/evidence.py`, `services/jobs.py`, `protocols.OnSigned` |
| D44 | **Standalone credentials: inspect, rotate, and one answer rule** (Mike, 26 October, ISS-08 [#21](https://github.com/Cloud-SPE/Network-Engineering-SPE/issues/21), from John's plan). (1) `GET /v1/admin/keys/{key_id}` shows a key without its secret. (2) `POST /v1/admin/keys/{key_id}/rotate` replaces a key at once, in one transaction: the old token fails immediately, and the new key keeps the kind, actor, application and permissions, with an optional new label (`201`, token shown once). No overlap window, no re-scoping. (3) Every job and cost route checks the operation's permission before any lookup (`403`), then ownership (`404` for another actor's or a missing job), `result` and `submit` included. (4) An admin lists every actor's jobs in its application, like the cost reads. (5) A usage report needs `jobs.run` only. (6) `KeyService` logs `keys.bootstrapped`, `keys.issued`, `keys.rotated` and `keys.revoked` with the acting admin, never a token or hash | `services/keys.py`, `services/jobs.py`, `services/costs.py`, `http/app.py`; [access.md](../contracts/access.md); [plan](../exec-plans/active/iss-08-standalone-credentials.md) |
